Counting API usage is harder than it looks

NutriKit gives every API key a monthly allowance. My first idea for counting usage had a race condition. This is what I ended up doing.

NutriKit is a nutrition API I built. You describe a meal in text, voice or a photo, and you get back the foods, portions and nutrients. Each API key has a monthly token allowance. A food search costs 1 token, and a photo can cost up to 20 because it calls an AI model.

I thought counting this would be the easy part.

The simple version

const used = await getUsage(key);
if (used + cost > allowance) throw quotaExceeded();
const result = await handleRequest();
await addUsage(key, cost);

Looks fine. The problem shows up when requests run at the same time, which is completely normal for an API. Say a key has 10 tokens left and sends ten photo requests together. All ten read used before any of them updates it. All ten pass the check. All ten call the AI model, and the key ends up way over its limit. And I'm the one paying for those AI calls.

Reserve first

The fix was to make the check and the update a single database statement. Before doing any work, a request reserves its cost, and the reservation only goes through if it still fits:

INSERT INTO usage_periods AS p (subject, period_start, used)
VALUES ($subject, $period, $cost)
ON CONFLICT (subject, period_start) DO UPDATE
  SET used = p.used + EXCLUDED.used
  WHERE p.used + EXCLUDED.used <= $limit
RETURNING used;

If no row comes back, the request gets a 429 and the handler never runs. Postgres applies the updates on that row one at a time, so out of ten parallel requests, only the ones that actually fit get through.

Then settle the real cost

The final cost isn't always what was reserved. AI calls depend on how many model tokens were used. One endpoint accepts either a photo or text, so it reserves the photo price and settles lower if it turns out to be text. After the request finishes, it adjusts the counter by the difference and writes the charge into a usage history table, both in one transaction.

What should a failed request cost?

This part needed more thinking than the code did.

If a request fails validation, times out, or the AI provider is down, the reservation is released and it costs nothing. But if the AI provider already did the work, for example it looked at the photo and decided it's not a nutrition label, those model tokens were really used. So those get charged, and the response includes an X-Tokens-Charged header that says how much.

I also wrote all of this down in the docs. If people get charged and can't see why, they stop trusting the API.

Being able to fix it later

The running counter is fast, but it can drift. If the server crashed between reserving and settling, the counter would stay a bit high. I'm fine with it going in that direction, because a counter that's too high never lets anyone overspend. And since every charge is also in the usage history, there's a reconcile command that rebuilds a month's counters from it.

What I'll keep in mind

Now, any time my code reads a value, makes a decision, and then writes, I stop and ask what happens if two requests do this at once. Usually the answer is to move the decision into one atomic query, and keep a history table so the fast number can always be rebuilt.
