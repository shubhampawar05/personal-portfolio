What I learned building my first RAG app

I built DocChat during a GenAI cohort. You upload a PDF and ask questions about it. Simple idea, but I got a lot of things wrong first.

DocChat lets you upload a PDF or text file and then chat with it. Answers only come from your file, with the page number after each fact. The stack is Node.js, Express, LangChain, OpenAI for embeddings and chat, and Qdrant as the vector DB.

It's a small project, but I got quite a few things wrong before it worked well. These are my notes from that.

It's two flows, not one

When I started, I thought of RAG as one long pipeline. It made a lot more sense once I split it into two parts that just share a database:

INDEXING (once per file)               QUERYING (every question)
file -> load -> split into chunks      question -> embed -> search Qdrant (top 5)
     -> embed (OpenAI) -> store              -> prompt + chunks -> LLM -> answer

Indexing happens once per file. Querying happens on every question. Whenever something broke, the first thing I asked myself was "which half is this in?" That alone cleared up a lot of confusion.

Chunk size matters more than I expected

You can't embed a whole PDF as one vector. Embedding models have an input limit (around 8k tokens), and even if they didn't, one vector for a full document mixes every topic together. Search can't find the one paragraph you actually need.

I used LangChain's text splitter with 1000 character chunks and 200 characters of overlap. Smaller chunks matched more exactly but lost the context around the answer. Bigger ones kept context but matched loosely. 1000/200 was a good middle for the documents I tested with. The overlap is there so a sentence that gets cut at the end of one chunk is still complete in the next one.

const splitter = new RecursiveCharacterTextSplitter({ chunkSize: 1000, chunkOverlap: 200 });

One thing I'm glad I did early: for PDFs I create one document per page before splitting, and keep the page number in the metadata. That's the only reason the app can show "p. 3" later. If you lose it while loading the file, there's no way to get it back.

Same embedding model on both sides

Obvious once you know it. The question has to be embedded with the same model you used for the documents. Different models give vectors that can't be compared, and nothing throws an error. You just get bad matches and wonder why. So now the model name lives in one place and both parts read it from there.

Bad answer? Check retrieval first

Whenever an answer was wrong, my first reaction was to go and change the prompt. Most of the time the prompt wasn't the problem.

Qdrant returns a similarity score with every chunk, so I started logging those. If the scores are low, the right text never reached the model, and no prompt is going to fix that. It's the chunking, the question, or the document itself. If the scores look good and the answer is still wrong, then I look at the prompt.

Honestly this habit saved me more time than anything else in the project.

Stopping it from making things up

Even with the right chunks, the model will happily answer from its own knowledge if you let it. My system prompt tells it to use only the context it's given, to cite each fact as (file name, p. N), and to say clearly when the answer isn't in the documents. Temperature is 0, because here I want facts, not creativity.

I also wrap each chunk in a tag with its source, so the model can see where every piece came from:

<context>
<excerpt id="1" source="handbook.pdf, p. 3">...</excerpt>
<excerpt id="2" source="handbook.pdf, p. 7">...</excerpt>
</context>

For answer length, I first tried maxTokens. Bad idea. It's a hard cut, so the answer just stops in the middle of a sentence. Asking for a short answer in the prompt works much better, because the model plans for it. maxTokens is still there, but set higher, as a safety net and to cap the cost of each answer.

Deploying it

Locally, Qdrant runs in Docker. Render's free plan can't run that, so the live version uses Qdrant Cloud, which is why the DB URL and key come from environment variables. And since every question costs me OpenAI credits, the live site has a password and a rate limit. On localhost I never thought about cost. Once it was public, I had to.

What I want to try next

Basic RAG works well when the question is clear. It struggles with vague ones. In a later project I tried query rewriting, where one question gets turned into a broader version plus a few smaller sub-questions before searching. After that I want to try hybrid search (keywords plus vectors), reranking, and a small set of test questions, so I can actually measure whether a change helped instead of trying a few questions by hand.
