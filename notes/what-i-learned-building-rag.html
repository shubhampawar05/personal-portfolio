What I learned building a simple RAG app

Six lessons from building DocChat, a small app that lets you chat with your documents — and why most of my bugs turned out to be retrieval, not the LLM.

DocChat is the first RAG app I built: you upload a PDF or text file, then ask questions about it. Answers come only from your documents, with a page citation after each fact. It's small — a Node.js server, LangChain, OpenAI and Qdrant — but almost every decision in it taught me something.

The two halves of RAG

The thing that made RAG click for me was seeing it as two separate pipelines that share one database:

INDEXING (once per document)           QUERYING (every question)
file -> load -> split into chunks      question -> embed -> search Qdrant (top 5)
     -> embed (OpenAI) -> store              -> prompt + chunks -> LLM -> streamed answer

Indexing is slow and happens once. Querying is fast and happens on every message. Most of the bugs I hit made sense once I asked which half they were in.

1. Chunking is a trade-off, not a setting

Why split at all? Two reasons. One vector for a whole book blurs all its topics together, so search can't find the one paragraph you need. And embedding models have an input limit of around 8k tokens anyway.

I settled on about 1,000 characters per chunk with 200 characters of overlap. Smaller chunks match questions more precisely but lose context. Bigger ones keep context but match vaguely. The overlap means a sentence cut at a chunk boundary still appears whole in one of the two neighbours.

const splitter = new RecursiveCharacterTextSplitter({ chunkSize: 1000, chunkOverlap: 200 });

One detail I'm glad I got right early: for PDFs I create one document per page before splitting, and keep the page number in the metadata. That's the only reason the app can say "p. 3" later. If you throw that away at load time, you can't get it back.

2. Use the same embedding model on both sides

The question has to be embedded with exactly the same model you used to index the documents. Different models put text in different vector spaces, so comparing them is meaningless — and nothing errors. You just get bad results. Now I keep the model name in one config value that both halves read.

3. When answers are bad, check retrieval first

My instinct was to blame the LLM and tweak the prompt. Usually that was wrong. Qdrant returns each chunk with a cosine similarity score, and logging those scores became my main debugging tool:

  • If the scores are low, the right chunks never reached the model. That's a retrieval problem — chunking, the query, or the document itself.
  • If the scores are high and the answer is still wrong, then it's the prompt or the model.

This one habit saved me more time than anything else in the project.

4. The prompt is what stops hallucination

Retrieval gives the model the right text, but the model will still happily answer from its own memory unless you tell it not to. My system prompt says to use only the provided context, to cite each fact as (file name, p. N), and to say so when the documents don't contain the answer. I run it at temperature: 0, because when you're answering from documents you want the most factual output, not creativity.

I also wrap each retrieved chunk in a labelled tag, so the model can see exactly where each piece came from:

<context>
<excerpt id="1" source="handbook.pdf, p. 3">...</excerpt>
<excerpt id="2" source="handbook.pdf, p. 7">...</excerpt>
</context>

5. Control length with the prompt, not max tokens

I first tried to keep answers short with maxTokens. Bad idea: it's a hard cut-off, so the model stops mid-sentence. The prompt asking for a short answer is the real control — the model plans a short answer and finishes it. maxTokens is now just a safety net set above that, which also caps the cost of each answer.

6. Deploying changes the architecture

Locally, Qdrant runs in Docker. Render's free tier can't run that, so production uses Qdrant Cloud — which meant my code had to read the database URL and API key from the environment from day one. And since every question costs OpenAI credits, the public site has a password and a rate limit. Shipping something publicly makes you think about cost in a way localhost never does.

What I'd do next

Simple RAG gets you surprisingly far, but its weak spot is retrieval on vague questions. In a follow-up project I tried query rewriting — turning one question into a broader "step-back" question plus a few focused sub-questions before searching. The next things on my list are hybrid search (keywords plus vectors), re-ranking, and a small eval set so I can measure changes instead of eyeballing them.
