Reserve, then settle: metering an API without overspending

Checking a user's balance before a request looks correct — until ten requests arrive at once. How NutriKit counts usage safely under concurrency.

NutriKit is a nutrition API I built: describe a meal in text, voice or a photo and it returns matched foods, portions and nutrients. Developers get an API key with a monthly token allowance — 1 token for a food search, up to 20 for a photo, which calls an AI model.

Counting usage sounds trivial. It isn't, and the reason is concurrency.

The obvious version is wrong

My first instinct was check-then-act:

const used = await getUsage(key);
if (used + cost > allowance) throw quotaExceeded();
const result = await handleRequest();
await addUsage(key, cost);

Picture a key with 10 tokens left sending ten photo requests at once. All ten read used before any of them writes. All ten pass the check. All ten call the AI model. The key ends up 190 tokens over its allowance, and I pay for the model calls. Parallel requests are normal for an API, so this would happen in practice, not just in theory.

Step 1: reserve, atomically, before any work

The fix is to make "check" and "take" a single database operation. Before a request does anything, it reserves its cost with one statement that only succeeds if the cost still fits:

INSERT INTO usage_periods AS p (subject, period_start, used)
VALUES ($subject, $period, $cost)
ON CONFLICT (subject, period_start) DO UPDATE
  SET used = p.used + EXCLUDED.used
  WHERE p.used + EXCLUDED.used <= $limit
RETURNING used;

If no row comes back, the reservation didn't fit: the API answers 429 quota_exceeded and the handler never runs. Postgres serialises the updates to that row, so ten parallel requests can't all squeeze through — only as many as actually fit.

Step 2: settle to the real cost

A request doesn't always cost what was reserved. An AI call's price depends on how many model tokens it used, and one endpoint accepts either a photo or text, so it reserves the expensive case and settles down. After the handler finishes, the request settles: it adjusts the counter by the difference between reserved and actual, and writes the charge to a usage history table — in one transaction.

Step 3: decide what failures cost

This was the part that needed the most thought:

  • A request that fails validation, times out, or can't reach the AI provider releases its reservation and costs nothing.
  • But if the AI provider already did the work — say it looked at the photo and decided it wasn't a nutrition label — those model tokens were really spent. So those are charged, and the response says how much in an X-Tokens-Charged header.

Being explicit about this, and documenting it, mattered more than the code. API users get angry about charges they can't explain.

Step 4: keep a way to repair it

The running counter is fast but could drift — if the server crashed between reserving and settling, the counter would stay slightly high. Two choices make that safe:

  • Errors go in the customer's favour: a lost settlement leaves the counter high, never letting someone over-spend.
  • The usage history is the source of truth, and a reconcile command rebuilds any month's counters from it.

What I took away

Any time you read a value, decide, then write, ask what happens if two requests do it at the same time. The fix is usually to push the decision into a single atomic database operation, and keep an append-only history so you can always rebuild the fast counter if it goes wrong.
